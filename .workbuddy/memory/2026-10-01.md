## 19:35 【重要根因】新建向导「点题材没反应」= WXML wx:for 变量名写错

用户反馈：AI 推荐题材里点「都市」没反应，自己点上面的题材标签也没反应，要求支持多选且必须可见反馈。

**真正的根因（一句话）**：`wizard.wxml` 里写的是 `class="chip {{genre===t?'on':''}}" wx:for="{{topics}}"`，但 **`wx:for` 只提供 `item` / `index` 两个默认变量，`t` 在模板作用域里根本不存在** → `genre===t` 恒为 `false` → 选中态 `on` 永远不亮。**点击其实生效了（数据变了），只是视觉上零反馈**。同类 bug 还有第②步目标读者 `{{reader===r?'on':''}}`（`r` 同样未定义），所以读者也点不亮。第③步签约用的是字面量 `{{contract==='signing'?'on':''}}`，所以它一直是好的 —— 这个对比正是定位线索。

**教训**：WXML 里引用未定义变量**不报错、不警告，静默变 undefined/false**。凡遇「bindtap 明明绑了但界面无变化」，第一件事就是核对 wx:for 的变量名（默认 `item`，自定义要用 `wx:for-item` 声明）。

## 20:45 部署脚本 4 个真 bug —— 「部署成功但接口 404」的完整根因链

现象：部署日志显示 `npm install / prisma db push / build exit=0`、e2e `5/5 通过`，但新接口 404，旧接口正常（服务跑旧 dist）。逐个挖出 4 个独立 bug，全部已修：

1. **打包未排除本地 db** → `prisma/novel.db` 被上传，服务器解包覆盖被占用文件报 `Can't unlink already-existing object: Permission denied`，tar 返回非 0。**修**：tar 加 `--exclude='prisma/*.db' --exclude='prisma/*.db-journal'`。
2. **`&&` 把关键步骤整条断掉** → 原步骤 3 `cd ... && tar ... && call install.cmd`，tar 一失败后面全跳过，**依赖/编译根本没跑**；脚本读到的 `exit=0`/`ALL_DONE` 来自**上一次的 install.log**（时间戳 17:33 暴露真相）。**修**：一律改 `&`。
3. **编译在服务运行时执行** → node 锁住 Prisma query engine，`prisma generate` **exit=1**（静默失败，Client 不含新字段 → 新列读写全挂）。**修**：部署顺序改为 **停服务 → 解包/依赖/generate/db push/build → 起服务**。
4. **Git Bash 路径转换** → 本机 Git Bash 会把命令里的 `C:\erp\x` **自动转成正斜杠** `C:/erp/x`，且 `/d` 开关被当盘符转换。于是 `cd /d C:\erp\novel-backend` 报「命令语法不正确」，`call C:/erp/novel-install.cmd` 报「不是内部或外部命令」（**call 不吃正斜杠**）。
   **诊断金句**：`echo [C:\erp\novel-install.cmd]` 输出 `[C:/erp/novel-install.cmd]` 一眼看穿。
   **修**：服务器命令一律用 `C:/...` 正斜杠 + `cd`（**不要 `cd /d`**），**不要 `call C:/...`**，直接写命令序列。
   附带：服务器 PATH 无 System32 导致 `netstat`/`taskkill`「系统找不到文件」，改用 `schtasks /end`（已足够释放端口，实测端口确实释放）。

**新脚本结构**：1 打包 → 2 上传 → **3 停服务** → 4 解包+装依赖+generate+db push+build → 5 起服务 → 6 自检。上述 6 条铁律已写进脚本头部注释，避免下次重踩。

**排查心法（重要）**：部署脚本"显示成功"≠"真的成功"。`exit=0` / `ALL_DONE` 可能来自**陈旧日志文件**——务必核对日志**时间戳**是否为本次，不要只看关键字。另外 `&&` 链在中间失败时会静默跳过关键步骤。

**环境事实**：测试服 120.79.174.44 的 SSH(22) 本时段**时通时断**（多次 Connection timed out，需加 `for i in 1 2 3` 重试），但 3001 的 HTTP 一直可用；ssh 输出是 GBK，grep 会判为 binary，需加 `-a`。

### 8）真联网查重 + 360 式即时加分 + 「修复中」卡死（2026-10-01 深夜）
- **真联网查重（作者怀疑 AI 凭印象编作品名）**：`SearchService` 正式接入 `checkDuplicate` 与 `batchVerifyTitles`。
  - `searchNovel()` 并发发 3~4 个查询（`${t} 小说` / `site:fanqienovel.com` / `site:qimao.com`）—— 串行 await 太慢，批量预检 4 个候选名会到几十秒。
  - 抓到的在榜作品存 `HotBook` 表（累加 hits），之后 `localMatches()` 本地比对，结论稳定可复现。
  - **硬判定压过 AI**：`hardClash()` 用 `diceSimilar` 算相似度，高=≥0.85、中=≥0.7 或「命名结构相同且 ≥0.5」；`batchVerifyTitles` 里硬判定 risk 若高于 AI 给的就覆盖 —— 否则推荐出去的名字换个还是撞。
  - 抓不到结果时降级并在 riskNote 标注"未联网"，不阻塞流程。服务器实测 Bing 可抓（status=200，9 个 b_algo 块可解析）。
- **360 式打分（作者：修一个分数加一点）**：分数不再用 AI 印象分，改由矛盾条数推：`scoreOfIssues()` 高-8/中-4/低-2，撞车 high-12/mid-5。
  - **【坑·已修】基准错位**：老 auditJson 的 score 是 AI 印象分（72），扣分制算 9 条只有 56 → 修掉一条显示 64，**分数不升反降**。解决：保留旧基准偏移量 `新分 = 扣分制新分 +（旧分 − 扣分制旧分）`。实测 72 → 80（+8）、条数 9→8。
  - 新增 `POST /novel/:id/audit-resolve {quote}`：把这一条从 issues/autoFix/human 划掉、累加 `resolvedCount`、重算分并落库（退出小程序角标也是减过的）。前端 `dropIssue()` 乐观更新 + 以服务端返回为准。
  - UI：标题下加「已修 N 处 · 还剩 M 处 · 当前 X 分」，每条按钮带「+8分」提示。
- **「修复中」卡死（作者：那个显示修复中，没被修复）**：
  - 根因①：全列表共用一个 `fixBusy` → 点第 3 条时第 1/2/4 条也一起显示"修复中…"，且任务卡住后整列永远点不动。改为 `fixingIdx`（-1=没有），只有真正在修的那条变灰显示"⏳ 修复中…"，其它照旧可点；`onHide/onUnload/applyAudit` 都重置。
  - 根因②：AI 重写后正文一个字没变，却照样算"已修"。现在 `fixOne` 改完拿 `before/after` 正文比对验收：完全没变 → 提示"这条没改动，再点一次"，不划掉、不加分。
